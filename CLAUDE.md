# Dive

A Rust CLI agent with a plan-based execution engine. Cargo workspace, seven crates. GitHub: `loon-rocks/dive`.

**Positioning: plans first.** The plan pipeline is the core product. "The workbench" means the workbench TUI (`dive wb`; `dive wb plan|agent|tool` opens a mode directly) — the review/debug surface for plans; the agent loop (`ask`/`chat`) is the conversational layer for probing tools, prototyping, and exercising plans. Frame features and docs accordingly, and keep that vocabulary: never call `ask`/`chat` "the workbench".

**The documentation under `docs/` is the canonical reference** for behavior, file formats, and CLI surface — read it before changing the corresponding code, and update it in the same PR as any behavior change. Start with `docs/getting-started/concepts.mdx` and `docs/plans/overview.mdx`. Published via Mintlify from this repo (`docs.json` is the nav manifest; monorepo contentDirectory `docs/`; Mintlify deploys the `docs-live` branch, which the release workflow moves to each release tag, so docs merged to `main` go live with the next release). The site is public — it is the documentation for a public, open-source library, so treat every page as user-facing.

## Build & test

Tooling is managed by mise; plain `cargo` works, including rust-analyzer.

```bash
mise run build          # cargo build
mise run test           # all workspace tests
mise run lint           # fmt --check + clippy -D warnings (run before committing)
mise run run -- <args>  # run the CLI
mise run install        # release build onto PATH; on macOS, re-signed with $DIVE_DEV_SIGN_IDENTITY when set (local dev only, so Keychain "Always allow" survives rebuilds; never used by CI or releases)
mise run release:patch  # prepare a release for review (also :minor / :major); release:publish ships it — see RELEASING.md
```

CI (`.github/workflows/ci.yaml`) runs lint + tests on ubuntu-24.04 and macos-15 for every push/PR touching non-docs paths; sccache keeps cache-key rotations from recompiling the world. Tags `v*` trigger `release.yaml`: binaries for macOS arm64 + Linux x86_64 with checksums, plus the `ghcr.io/loon-rocks/dive` container image (Dive + git/jq/gh; `workflow_dispatch` with a `tag` input re-mints an image for an existing release).

**Dive dogfoods itself on every PR** (`.github/workflows/dive-checks.yaml`): the `docs_drift` plan fails the check (exit 4) on undocumented crate behavior changes, the `format_drift` plan fails it on a schema change to a versioned file without a version bump (see RELEASING.md, "Version bumps"), and `dive_review_9000` maintains eight passes' worth of findings over a wide-context diff as living review threads (prior findings read back by hidden payload marker, fixed ones resolved with a reply, human-dismissed ones treated as declined, only new ones posted) plus a marker-keyed summary comment — both run from the repo-carried `./.dive/` inside the release image (needs the `ANTHROPIC_API_KEY` repo secret), and a `dogfood-files` job runs `dive config check` plus `dive plan validate` over `./.dive/` in that same pinned image, so the image pin and the repo's own file versions move together. `dive_review_9000` is a composition: `plan__dive_review_core` is the locally runnable review engine (git-only, over the worktree-capable `user__repo_*` tools in `.dive/tools/`) and `plan__dive_review_thread_audit` settles thread lifecycle, called via a route step only when prior findings exist. `.dive/` is partially tracked: config, plans, and tools are committed; everything else under it stays ignored. Expect the drift gate to hold you to the docs-parity invariant below.

## Architecture facts that bite

- **Tool catalog namespacing**: `<server>__` (MCP), `user__` (user tools), `builtin__` (built-in tools), `<pack>__tool__` (installed packs), `plan__` (plan docs), `agent__` (named agents: the built-in `chat` and agents dirs; plan steps and the planner catalog only — except `agent__chat`, which the planner catalog and tool search never offer and `builtin__check_plan` rejects, though hand-written plans may call it; dispatched by `Pipeline::call_agent` in a child pipeline with an allowlisted toolset and a depth cap of 3), plus reserved bare names `plan_and_execute`, `exit`, `route`, `filter`, `map`, and `reduce`. Native authoring tools (`builtin__validate_plan`, `search_tools`' `builtin__catalog_tools`, `builtin__score_candidates` and `builtin__describe_tools` in `pipeline/search.rs`, and `compose_plan`'s `builtin__compose_context`, `builtin__check_plan`, `builtin__question_form` and `builtin__find_tools` in `pipeline/compose.rs`, and the drafters' `builtin__try_tool`, `builtin__save_tool` and `builtin__save_agent` in `pipeline/drafter.rs`, which the agent toolbox also exposes to conversation agents) are Rust, intercepted by `Pipeline::call_native`, and not YAML-overridable. Everything shares one `ToolRegistry` catalog (`CompositeRegistry` merges sources); shape recording wraps the base. Packs (`[packs.<name>]` entries, installed by `dive pack add` as plain copies under a layer's `packs/` with a `packs.lock`, loaded by `dive-core/src/packs/`) reuse the user-tool format and registry with a `<pack>__tool__` prefix; you change a pack tool by editing its copy. A pack's exec tools run with `DIVE_PACK_DIR` set to the pack's installed directory (`UserToolRegistry::with_pack_dir`), which is how a pack ships scripts or binaries. One override model for every kind: a tool file in a tools dir's `builtin/` subdirectory replaces the built-in tool it names, under its `builtin__` name (`user_tools::apply_tool_overrides`; a top-level file is always `user__`), a plan file replaces a built-in plan with the same identifier (`doc::add_builtin_plans`, built-ins are the lowest catalog layer), and agent files replace built-in agents by name; `show` commands report the source.
- **Conversations** (`agent/conversation.rs`): `chat`/`ask` run `Conversation::run_turn` over the thread's entries — the active agent's `tools` allowlisted over the toolbox catalog, `agent__<name>` per `subagents` (run via `Pipeline::run_subagent`, logged as a `subagent_run` entry, never in a view), `transfer_to_<name>` per `handoffs` (stop tools; the target continues the same turn unless the call passes `wait_for_user: true`, which ends the turn with the target active and the caller's text as the reply — front_desk uses it after loading a plan, so plan_editor never starts work unprompted; after 4 handoffs the holder's handoff tools are withdrawn). An agent handed the conversation by another gets a runtime `transfer_back` (no file entry; recorded with `via: transfer_back`, never offered back the other way), which is how `network_drafter` returns to `plan_editor` after saving a tool a plan step needed. Tools and agents the drafters save live in a runtime-wide `pipeline::Drafted` (served by `DraftedTools` ahead of the static registries, merged into `Pipeline::live_catalog` and `AgentSet::with_drafted`), so a save is usable in the same session without a reload. In the workbench, all drafting goes through the architect `network_drafter`: it interviews (one question at a time, each with its guess and a confidence number, ending in a restate the user confirms), puts a sketch in the pane with `workbench__set_sketch` (restate, nodes with job/model role/principles, edges), pushes back once on wasteful designs, then runs the workbench `tool_drafter`/`plan_drafter`/`agent_drafter` as typed subagents (input `{node, notes, answers}`, output `{name, status: drafted|question|failed, summary, problems, questions}`) — builders never talk to the user or save. The design principles (decision models first among them) are one fragment, `{{rules.design}}` (`dive-core/src/prompts/design_rules.md`, a `global_fragments()` entry), included by network_drafter, network_editor, the three workbench builders and the global tool_drafter/agent_drafter; whether a decision model is available is the last line of `agents::model_roles`, which the `network` attachment gives its readers and `agents::design_context` (the context hook of attachment-less conversations from `Runtime::conversation`) gives any agent whose prompt includes `{{rules.design}}`. The pane holds a `network::Network` (`DraftState.network`, `workbench/network.rs`): sketch nodes keyed by kind+name, each draft checked against `network::overlay` (a pipeline clone where drafted and still-stub nodes exist, so drafts may name nodes not drafted yet), and `set_artifact` refuses a file that isn't a sketched node once a sketch exists; a plan goes to a network node when there's a sketch or a node of its identifier, else to the plan pane. `workbench__test_network` runs one turn (or plan run) over the overlay after the user approves, each agent on its own model, via a cycle-free clone of the workbench conversation (`artifact::Tester`); `workbench__fail_test` marks it failed; `workbench__save_network` (Ctrl+S; `x` twice discards) needs every sketched node drafted without problems and a passing test since the last change (`untested` aside), asks once, and writes tools, then plans, then agents. The `handoff_guard` refuses handing off away from `network_drafter` while drafts are unsaved. Network nodes carry an `Origin` (new, file, builtin, pack) and the `base` file they were opened from; only changed nodes (`yaml != base`) count as unsaved, are checked for problems, or are saved. `artifact::existing` opens user, built-in and pack tools, agents and plans (pack items under their bare names, resolved to `<pack>__<kind>__<name>` by the overlay); saving writes an opened item back to its file, a built-in tool to `tools/builtin/<name>.yaml` (a built-in agent or plan to a file of the same name), and a pack item to its installed copy, and the result (`artifact::Saved`) names each file's destination (`file`/`override`/`pack`/`new`). Edit threads (`Start::Edit { items, evidence }`, through `Runtime::open_thread` only — the terminal workbench refuses it) start with `network_editor` (reads `network` and `evidence`; diagnoses the cause as a design choice, picks the smallest fix on a patch → restructure a portion → rethink the item's role ladder, offers a rework beside the patch through `workbench__propose_designs`, hands builders either one patch or a portion plus its mini-sketch in `notes` — the builders' patch and rework modes keep everything else byte-identical — asks to attach more items, tests against the evidence, never writes files) and are a network without a sketch: items opened at the start are recorded as the network attachment's `opened` list and opened before replay on reopen, a save keeps the items open (rebased on what was written), a discard reverts them, and `workbench__load_artifact` into such a network needs a `reason` and the user's approval (plans load as network nodes whenever the network has nodes). `ChatSession::begin()` runs the first turn without a user message (`Conversation::run_turn_from(.., None)`, from the agent's context note alone). In `dive chat` the global drafters' saves ask through the interlocutor first. `view(agent, entries)` gives an agent the user's messages, other agents' text and handoffs as merged user-role notes, plus its own messages verbatim. `[prompts].chat`/`.workbench` are deprecated (warned; ignored when equal to the shipped default or when an agent file overrides the agent). Conversation subagents run inside the conversation (`Conversation::run_subagent`, over its catalog and context hook), not via `Pipeline::run_subagent`, which serves plan-step `agent__` calls. The workbench is a conversation over `workbench/agents/*.yaml` (front_desk, network_drafter, plan_drafter, plan_loader, plan_editor, network_editor, and workbench versions of tool_drafter/agent_drafter; `agents::builtin_sources()` also feeds `dive agent`), starting from `agents::Start` (bare `dive wb` → `front_desk`; `plan` → `plan_editor` with a plan else `network_drafter`; `agent`/`tool` → `network_drafter`, with a named file opened as a network node via `artifact::open_existing`), with context sections from its attachments (`attachment::context_hook`: an agent gets the network sections when its YAML says `attachments: [network]`, the current plan when it says `[plan]`, and the evidence when it says `[evidence]`), whose sections reach a conversation agent as a `context:<agent>` history note, recorded only when they change and shown only to that agent, so the system prompt and earlier turns stay a cacheable prefix (subagents still get them in the system prompt). Workbench agents list tools explicitly — never `"*"`, and plan_editor calls no real catalog tools apart from the `web` pack's `web__tool__search`/`web__tool__fetch`, which the drafters and plan_editor list and simply lack when the pack isn't installed (it uses `workbench__describe_tool`, which reads `Pipeline::planner_tool_defs` — control steps included — and on a miss names an unconfigured server prefix and the closest real tools, telling the agent to stop guessing). New plans come from the built-in `compose_plan` plan (needs → search → one draft call → `builtin__question_form` + an `ask` only when the draft guessed values → up to three `builtin__check_plan` patch rounds until settled (valid, no pending `search`, answers in), each carrying the answers and able to request tools via `search` → `builtin__find_tools`; the workbench captures the returned plan (`tools::ComposedCapture`) so `set_draft` with no `plan` publishes it untouched; `plan__compose_plan` returns `missing` with no plan when no tool fits, which the plan_drafter returns as `failed`), run by the `plan_drafter` builder, published with `workbench__set_artifact {kind: plan}` (in the plan pane it refuses unsaved changes without `overwrite_draft`); the toolbox pipeline carries a `UiInterlocutor` so an `ask` in a plan the agents call reaches the UI.
- **Plan invocation lives in the pipeline**, not the toolbox: `Pipeline::call_plan`/`call_planner` (boxed recursive futures). The toolbox is a thin adapter for the agent loop. **Plans compose**: `plan__*` and `plan_and_execute` are valid step tools; the pipeline call stack detects cycles and caps depth at 8.
- **Control steps** (`exit` gates, `route` forks, `filter` selection, `map`/`reduce` iteration) are executor-intercepted, never dispatched to a registry. `exit`/`route`/`filter` share one gate grammar (`pipeline/condition.rs`): a logical value/op/to condition (spelled `when` on exit, `if` on route, `where` on filter — evaluated per item there), `infer` (yes/no verdict via the `judge` role; per item on filter, with `concurrency`), or `decide` (a decision-model gate via the `decider` role: a likelihood checked against `min_confidence`, or — on `route` only, with `options` and `cases` — an N-way choice). `infer` and `decide` each refuse the other kind of model. Fired exits skip remaining steps *and the solver*; error exits → process exit code 4, `is_error` plan-tool results. `route`'s `then`/`else` (or `cases`) and `map`/`reduce`'s `do` share one body grammar (`pipeline/body.rs`): a single call or inline step list, rendered lazily (only the gate / `over` renders up front; only the chosen branch renders at all; map/reduce bodies render per item with `item`/`index` pseudo-roots, plus `accumulator` on reduce). Body-step results stay scoped (never in `state.results` — the step cursor and replan merge key on it) but count in `steps_executed`. Bodies may nest `agent`, `ask`, `filter` (its `item`/`index` shadow the enclosing body's inside its gate), `route` (`Pipeline::eval_route` runs against the body scope; its branch paths extend the body path, e.g. `E1/do.2/gate/then/E10`), and `exit` (ends the whole plan from any body); `map`/`reduce` never nest — bodies call `plan__*` for nested iteration. `filter` returns both halves (`items`/`dropped`), so selection narrows what runs next without losing what is known. `map`'s `onError: skip` (plan v2) leaves failed items out of `results` and lists them in `failed` (`{index, item, error}`, `failed_count`) instead of failing the step; exits and aborts still end the plan. `map`'s `concurrency` is the pipeline's only parallelism (plus filter's `infer` verdicts): items run via ordered `buffered(n)` and failures drain in-flight items rather than cancel; `reduce` is sequential by definition (fold).
- **Storage backends** resolve via `[storage].backend` / `DIVE_STORAGE` env (`file` default, `memory` for CI). The file store tolerates concurrent processes: whole files write via temp-file+rename, thread entry appends (`entries.jsonl`: `message`/`handoff`/`subagent_run`, each with `seq` and `author`; meta carries `owner`/`active`) are O_APPEND under a per-thread flock, shape writes are last-writer-wins (`seen_count` is advisory). Local filesystems only (flock over NFS is unreliable). The shape cache is read fresh at each planning attempt — never snapshot it at construction.
- **Secrets**: every `${NAME}` (config expansion, tool `env`, pack `requires.env`, the drafter's try-run prompt) resolves through a `SecretSource` — the trait lives in `dive-config::secrets` (dive-config can't see dive-core), the keyring-backed `CredentialStore` (service `dive`, account `NAME`), `ChainedSource` and `MemorySecrets` in `dive-core::secrets`; `secrets::system()` is env first, then the store, an empty env value never shadows a stored one, and an unavailable store (container, headless Linux, locked keychain, `DIVE_SECRET_STORE=none`) is a miss, never an error. Lookups are lazy, never cached, and a value is never logged, printed or written; `Resolved`'s `Debug` redacts it. `dive secret set|rm|list|show` render `dive_runtime::secrets`, which the desktop app calls directly; listing is derived from references (config layers read raw, so it works when the load fails), since stores can't be enumerated. A tool `env` entry is a string or `{value, description}` (`user_tools::EnvEntry`, tool v3); the description is markdown that rides on each `Reference` and `SecretEntry`. A `${NAME}` with no default is a needed secret (`user_tools::needed_secrets`, served per catalog name by `ToolRegistry::needed_secrets`); `workbench__test_network` and `workbench__try_artifact` collect them for every tool the test would reach (`workbench/secrets.rs`: plan steps, agent `tools` — a bare `*` covers only the network's own tools — subagents and handoffs) and, when any is unset, run nothing and return `status: missing_secrets`, leaving `NetworkView.waiting_on_secrets` set until a test runs. `mise run test` sets `DIVE_SECRET_STORE=none` so tests never touch the real Keychain — tests inject `MemorySecrets`.
- **Model roles**: `[models]` is one map of role name → model entry (`dive-config`'s `ModelRoles`). The standard roles `chat`, `planner`, `outliner`, `solver`, `repair`, `judge` are the keys the engine consults and fall back to `default` (`outliner` falls back to `planner` first, via `Role::fallback`); any other key is a custom role, same shape, selectable by name from prompt tools, `builtin__infer`, and `infer` gates, with no fallback (unknown name fails listing what is configured). A role carrying a `description` is what the planner catalog advertises. Structured output is provider-native (forced tool on Anthropic, json_schema with json_object fallback on OpenAI-compat) with one `repair`-role fix-up pass.
- **Telemetry is a sink, not a second event model**: `[telemetry]` (OTLP/HTTP, generic — Langfuse is just headers) builds `telemetry::OtlpSink` from the same `EventSink` events every other sink gets, teed in by `output::make_sink` / `telemetry::attach`; the run is the root span, steps/tools/generations parent by bus path and `llm_call.site`. `LlmCallEvent` (usage.rs) is what `llm_call` carries: site, role, provider, model, usage, cost, and optional request/response content, captured at `MeteredProvider` only when the ledger's `captures_content()` says so (`capture_content`). The exporter is process-global (`OnceLock`), initialised in `main` before the log subscriber (its OTLP logs layer hangs off it) and flushed by `telemetry::shutdown()` after the command returns — never inside a command, which would miss `usage_summary`. `EventSink::run_started`/`run_finished` bracket one trace (name, session id, input; then the deliverable) — `chat` and the workbench emit them per turn/run on a long-lived sink, `plan run`/`ask` set the same via `RunInfo` at attach; `telemetry::report_plan_result` is the plan-run helper. Sessions: thread id for `ask`/`chat` (the thread is created *before* the first turn and deleted if it fails), a per-launch uuid for the workbench. New `EventSink` methods must be added to `TeeSink` too.
- **Agents defer their tools** (`agent/deferral.rs`): every agent run (conversation turns and subagents, `agent__` plan steps, inline `agent` steps) sends the tools its list matches as `ToolSpec.deferred`, except standing ones (handoffs, `transfer_back`, `agent__` subagents, `Conversation.standing_tools` — the network attachment adds `workbench__*` — and the `[tools].always_loaded` matches), and adds `plan__search_tools` whenever anything is deferred. An agent's search runs `search_tools` on a pipeline clone whose `search_pool` holds that agent's deferred tools (`Pipeline::nested` clears the pool entering any other plan) with `schemas: false`; an agent that lists `plan__search_tools` by name (the drafters) searches the whole catalog plus its own deferred tools (`Pipeline::agent_search_pool`), keeping the schemas it asks for. Loading is history, not state: `ChatRequest.tool_references` (search call id → returned names) is recomputed from the messages on every request, so a reopened thread loads the same tools and nothing new is stored. Anthropic sends deferred tools with `defer_loading` and a referencing tool_result as `tool_reference` blocks only (the API refuses text beside them; the cached prefix survives a load); OpenAI-compat offers only standing plus referenced tools. Eval: `.dive/evals/deferred_tools`.
- **Execution gate + step events**: every real tool call at any depth funnels through the private `Pipeline::dispatch`; an optional `ExecutionGate` (Proceed/Skip{injected result}/Abort) is consulted there — never for control-step evaluation. `GateContext` carries the rendering scope (results map / layered body scope with pseudo-roots) — the debugger's locals. `on_tool_error` (defaulted → Fail) is the break-on-exception hook: Replace substitutes a value and continues (never replans); `tool_finished` reports the real call, `step_finished` the resolution. Aborts bypass replan/solver/error-summary and surface as `PipelineError::Aborted{state}` (nested plans propagate via `PlanCall.aborted`; nested aborts are never re-asked as errors). `EventSink::step_started/step_finished` carry rendered inputs and full results with bus-syntax paths (`E3/do.2/E10`) + the plan call stack. Draft-only planning (`dive plan draft`, MCP `dive_plan_draft`, the workbench) runs `compose_plan` (`call_plan(COMPOSE_PLAN, draft_input(..))`, its `plan` read with `plan_doc`; `--from` lends identifier, name and description). Its tools come from the built-in `search_tools` plan, run once per `data` capability: one decision-model choice question over every catalog tool via `builtin__score_candidates` (probabilities rank; >250 tools split into concurrent choices, then a final choice among everything reaching the threshold), BM25 when no decision model; queried with one capability alone (with the goal, every search ranked the goal's main tool first); no group stage, it cost recall; control steps are never searched, always offered; everything else deferred except `[tools].always_loaded`, default `builtin__infer` + `builtin__reshape`, the glue a single choice rarely returns as a second tool, which sit with the control steps in the cached system prompt. One-shot requests (one message, no tools) get no Anthropic tail cache breakpoint, since it would be written and never read; prompt-tool structured output is mechanically coerced (`user_tools::coerce_to_schema`: defaults for missing required fields, JSON-string objects parsed, `$PARAMETER…` wrappers unwrapped) before the repair call. Drafting never sees an existing plan's steps (there is no `revising` input; `plan draft --from` only lends identity), and `existing_plan` means executed-and-immutable and belongs to the replan prompt. Workbench debugger state (breakpoints/continue) lives UI-side in `DebugControls`; the oneshot reply is a `UiDecision` so continue-mode lands before the engine resumes.

- **Pre-rename names** (the project was graph until v0.17.0): `dive_config::legacy` is the only place they're read. `legacy::resolve` maps `.dive`, `~/.config/dive` and `~/.local/share/dive` to their `graph` counterparts when only the old one exists (config paths, `Workspace`, plan/tool paths and `data_dir` after load); `legacy::var` reads `GRAPH_<X>` when `DIVE_<X>` is unset; `CredentialStore` reads, lists and removes under the `graph` service too but writes only `dive`; pack v1's `requires.graph` migrates to v2's `requires.dive`; pack exec tools get `GRAPH_PACK_DIR` beside `DIVE_PACK_DIR`. Each fallback records a notice (`legacy::notices`) that `main` prints at exit on a terminal. Never move or delete old files. All of it goes at v1.0. Until a `dive` image exists, `dive-checks.yaml` runs the v0.16.0 `graph` image through a bridge step (symlinks `dive` and `.graph`); the release that publishes `ghcr.io/loon-rocks/dive` repins it and drops the bridge.

## Invariants to preserve

- **Error policy**: human-authored plans never replan; `EmptyData` (data ran out) is distinct from `BadPath` (plan defect) and never triggers replanning; output/silent plans fail hard on empty data — `exit` gates are the sanctioned way to pre-empt that. See `docs/plans/guides/handle-failures.mdx`.
- **Template dialect** is strict, typed, and logic-less; its contract lives in `dive-core/src/template/` tests and `docs/plans/template-language.mdx`. Changes to one must change both. Logic belongs in steps (user tools, exit conditions), never in templates.
- **Streams contract**: stdout carries only the deliverable (answer, output-mode JSON, `--json` envelopes); all progress/diagnostics go to stderr (`DIVE_EVENTS=jsonl` switches stderr to machine-parseable events). Exit codes: 0 ok, 1 failure, 3 needs-input, 4 exit-gate assertion. One sanctioned exception: `DIVE_EVENTS=github` prints a `::error::` annotation to stdout on *failing* `plan run`s (GitHub parses workflow commands from stdout only) — the choke point is `output::annotate_failure`.
- **MCP child processes** must be shut down via `McpManager::shutdown()` before the tokio runtime drops (async-Drop cleanup doesn't run during teardown; orphans attach to the user's terminal).
- **Commands return values, never print**: every command in `dive-cli/src/commands/` returns a `commands::outcome::Outcome` (machine `body`, `rejected` for domain refusals, optional `raw` stdout deliverable); `outcome::report` is the only thing that writes a stream and the only thing that reads `--json`. This is what lets the MCP server (`src/mcp_server/`) reuse each command without a second implementation — stdout there is the JSON-RPC channel, so any stray `println!` corrupts the protocol. Argument errors stay `anyhow`; domain rejections are `Outcome::rejected`.
- **Store access** goes through `Arc<dyn Store>`; commands never touch a concrete backend type directly.
- **File versions are independent of the binary version** (`docs/reference/file-versions.mdx`): config (`dive-config/src/format.rs`), plan, tool, and agent docs (`dive-core/src/format.rs`), and the data directory (`dive-store`'s `FORMAT` marker) each carry an integer top-level `version`; absent means 1. The typed models always match the *newest* version — older files pass through a forward-only migration chain on the raw document before deserialization (config layers migrate *per layer, before the merge*), and a file outside the binary's support window (`*_FORMAT_OLDEST..=*_FORMAT`) is refused by name before the schema is consulted. **Every schema change bumps**, additive ones included (a no-op migration): raise the constant, append a migration, add a `tests/fixtures/v<N>/` golden pair, and land it as a `(kind)!` commit so the changelog gives the new file version its own entry (the file-versions page states the contract and never lists versions). The window narrows only at a major release. Frozen fixtures for every version in the window must keep loading. Plan/tool/agent docs deny unknown keys at every depth — checked in the file loaders (`doc::check_step_keys`, `user_tools::unknown_tool_keys`, `agent::doc::unknown_agent_keys`), never on `Step` itself, which is also the planner's structured-output type and stays lenient.
- Prompts are prompt *surface*: planner-facing field names (`toolName`, `queryToAnswer`) are camelCase via serde and must stay aligned with the prompt text, which lives as markdown next to the code that embeds it (`dive-core/src/pipeline/prompts/`, `dive-core/src/prompts/`, `dive-runtime/src/workbench/prompts/`) and is pulled in with `include_str!` — edit the `.md`, not a Rust literal. Tool descriptions and exemplars are routing signals, not comments.
- **Never put link flags in env-wide RUSTFLAGS** — they poison build scripts (segfaulted x86_64 CI). Cargo quirk to remember: `rustc-link-lib` from a build script reaches downstream binaries but not the emitting package's own tests (those need `rustc-link-arg-tests`).

## Conventions

- Conventional commits (`feat:`/`fix:`/`docs:`/`chore:`/`ci:`) — the changelog is generated from them; subjects describe the user-visible effect. Enforced by `scripts/check-commit-subject.sh` via the `.githooks/commit-msg` hook (`mise run hooks`, once per clone) and the `commit-lint` workflow (PR title + every commit); the repo is squash-merge-only so the linted PR title is the subject that lands. See RELEASING.md. The scopes `config`, `plan`, `tool`, `agent`, and `store` are reserved for file-version bumps and require `!` (the linter refuses them otherwise); the changelog gives such a commit its own entry (`Config v2`) next to the binary's (`Dive v0.13.0`) — see RELEASING.md, "Changelog entries".
- **The changelog's audience is Dive's users, not Dive's developers.** Changes to this repo's own dogfooding under `.dive/` and `.github/` (the review plans, the drift gate, the CI workflows) ship to nobody, so they are typed `ci:` — never `feat:`/`fix:`/`refactor:` — which `cliff.toml` skips. `exclude_paths` there is only a backstop: it drops a commit only when *every* file is excluded, and plan edits often touch `CLAUDE.md` or `docs/` as well. A commit that changes both a crate and `.dive/` is a real release note — type it for the crate change and say so in the subject.
- Behavioral tests colocated per crate; mock LLM providers via `ModelRouter::with_providers`; scripted-response mocks for pipeline/agent tests.
- Every feature lands with tests and a lint-clean tree, then gets **live verification**: the MCP reference server (`npx @modelcontextprotocol/server-everything`) for tool mechanics, the user's real Linear workspace for plan behavior. Use the scratch pattern — a temp dir with `.dive/config.toml` overriding `data_dir` (and `DIVE_STORAGE=memory`) — to keep the user's real state out of test runs.
- Linux behavior is reproducible locally in a container (`podman run --rm -v $PWD:/repo:ro rust:1.94-trixie …`).
- Live example plans and user tools ship in the user's `~/.config/dive/{plans,tools}/` (sprint_analysis, project_status, urgent_issues; git_log, summarize) — useful as behavioral references.

## Worktrees

Always use worktrees for any coding work. Never make changes directly on the main branch. When spawning subagents, set `isolation: worktree` in their frontmatter.

Before finalizing work in a worktree, run the review engine over it and address any blocker or likely-bug findings: stage new files (`git add -N .`), then `dive plan run dive_review_core --input base=main` — it reviews the working tree against the merge-base with main and prints structured findings as JSON.
