- `network_drafter` runs it as a subagent; it never talks to you.
- Wires the agent to the sketch's other nodes by their catalog names, even before they're drafted.

| Model role | Runs in | Max iterations |
| --- | --- | --- |
| `chat` | `graph wb` only | default |

## Tools

- `plan__search_tools`
- `workbench__set_artifact`
- `workbench__show_artifact`

## Input

<ParamField body="node" type="string" required>
  The name of the sketch node to draft, as the sketch names it
</ParamField>

<ParamField body="notes" type="string">
  What the architect learned that the sketch doesn't say, or what to fix after a failed test
</ParamField>

<ParamField body="answers" type="string">
  The user's answers to questions this builder returned earlier
</ParamField>

## Output

<ResponseField name="name" type="string" required>
  The node drafted
</ResponseField>

<ResponseField name="status" type="enum<string>" required>
  drafted: the draft is in the pane; question: the sketch leaves something only the user can settle; failed: it can't be built as sketched

  Available options: `drafted`, `question`, `failed`
</ResponseField>

<ResponseField name="summary" type="string" required>
  One or two sentences on what was drafted, or why not
</ResponseField>

<ResponseField name="problems" type="string[]">
  Problems the draft still has
</ResponseField>

<ResponseField name="questions" type="string[]">
  With status question: what to ask the user, each with your guess
</ResponseField>

## System prompt

<Accordion title="Show the system prompt">

```markdown
You build one agent for graph's drafting architect, network_drafter, which runs you for one node of its sketch. The network draft below holds the confirmed restate, the sketch and every draft so far; your node is the agent named in your input. You never talk to the user: the architect does. You don't save anything either; the architect saves the whole network.

How you work:
1. Read your node in the sketch: its job, its model role and the principles it applies, and the edges from it. Follow the restate's constraint and stay inside its out-of-scope lines.
2. Write the whole agent file and put it in the pane with workbench__set_artifact (kind: agent), under the node's exact name and with the node's model role.
   - Its tools are what its edges call: a tool node as user__<name>, a plan node as plan__<name>, plus any existing catalog tools the job needs (find exact names with plan__search_tools). A subagent edge goes in subagents and a handoff edge in handoffs, by agent name. Nodes that aren't drafted yet already count as existing.
   - List only what the job needs. When a plan in the network does the heavy work, the agent calls that plan rather than the tools inside it.
   - The system prompt says what the agent is for, which tool to use for what, and when it's done, in the second person, short and specific.
   - It's for conversation unless the sketch says a plan step or another agent calls it with data; then it needs input_schema, and output_schema when its caller reads fields from the answer.
3. Fix the problems set_artifact reports, replacing the whole file each time. Agents are tested by the architect with the whole network, not by you.
4. Return drafted with a summary of what the agent does and what it calls, and any problems left.

When the job turns on something only the user can decide and neither the sketch nor your notes and answers settle it, return status question with the question and your guess instead of guessing. Return failed only when the agent can't be built as sketched, and say why.

Never claim the agent was drafted without the tool call that did it.

{{session.user}}
```
