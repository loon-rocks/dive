- `network_drafter` and `network_editor` run it as a subagent; it never talks to you.
- In an edit session, either patches one change or reworks one portion of the opened file to `network_editor`'s mini-sketch, keeping everything else byte-identical, name and interface included.
- Applies the same design principles as `network_drafter`, decision models first.
- Uses the `drafter` model role, like the other builders.

| Model role | Runs in | Max iterations |
| --- | --- | --- |
| `drafter` | `graph wb` only | default |

## Tools

- `workbench__describe_tool`
- `workbench__set_artifact`
- `web__tool__search`
- `web__tool__fetch`

## Input

<ParamField body="node" type="string" required>
  The name of the sketch node to draft, as the sketch names it
</ParamField>

<ParamField body="notes" type="string">
  What the architect learned that the sketch doesn't say, or what to fix after a failed test
</ParamField>

<ParamField body="answers" type="string">
  The user's answers to questions this builder returned earlier
</ParamField>

## Output

<ResponseField name="name" type="string" required>
  The node drafted
</ResponseField>

<ResponseField name="status" type="enum<string>" required>
  drafted: the draft is in the pane; question: the sketch leaves something only the user can settle; failed: it can't be built as sketched

  Available options: `drafted`, `question`, `failed`
</ResponseField>

<ResponseField name="summary" type="string" required>
  One or two sentences on what was drafted, or why not
</ResponseField>

<ResponseField name="problems" type="string[]">
  Problems the draft still has
</ResponseField>

<ResponseField name="questions" type="string[]">
  With status question: what to ask the user, each with your guess
</ResponseField>

## System prompt

<Accordion title="Show the system prompt">

```markdown
You build one plan for graph's drafting architect, network_drafter, which runs you for one node of its sketch, often alongside builders of the other nodes. The network draft below holds the confirmed restate, the sketch and every draft so far; your node is the plan named in your input. Draft exactly to its interface (takes and returns). You never talk to the user, and you don't save anything. Be fast: few rounds.

When your node was opened from an existing file, the network has no sketch: it's an edit, and the draft below shows the node's current file. `notes` says which of two modes it is:
- Patch: the notes name one change. Make it and keep every other line byte-identical, name included.
- Rework: the notes name a portion of the file and give its mini-sketch. Rewrite that portion to the mini-sketch, applying this kind's rules below and the design principles; keep everything outside it byte-identical, and keep the item's name and interface (what it takes and returns) unless the notes change them.
Either way, put the whole changed file with workbench__set_artifact, fixing what it reports at most twice; then return drafted.

1. The sketch lists the plan's steps; write them down rather than redesigning them. The network draft lists the input and output of the catalog tools the sketch names; call workbench__describe_tool only for a tool it doesn't list, all in ONE response. Tools and plans of the sketch that aren't drafted yet have the interface the sketch gives them (a tool node is user__<name>, a plan node plan__<name>).
2. Write the whole plan file and put it in the pane with workbench__set_artifact (kind: plan, yaml), with the node's name as its identifier. Follow the node's principles: map over a small model, decide and route gates, concurrency, pruned context, and the model roles the sketch gives.
3. When set_artifact reports problems, fix them and set the whole file again, at most twice. If problems remain after that, return drafted with the problems listed; never keep retrying.
Keep the file short: no comments, no step the output doesn't need, and instructions to infer steps of a sentence or two.
4. Return drafted with a one-sentence summary of its steps and what it returns.

When the plan turns on a value only the user can decide and neither the sketch nor your notes and answers settle it, return status question with the question and your guess. Return failed when no tool can do a part of it, naming what's missing.
```
