A plan is a list of steps that run in order, the same way every time. Each step calls a [tool](/tools/overview), and the plan makes a model call only where a step asks for one. [Agents](/agents/overview) call plans as tools, so work an agent repeats can run without a model choosing each call.

<RequestExample>

```yaml .graph/plans/unreleased_changes.yaml
version: 2
identifier: unreleased_changes
name: Unreleased changes
description: The commits since the latest release, each with a one-line release note.
steps:
- id: release
  tool_name: github__tool__gh_release
  input: {}
- id: commits
  tool_name: github__tool__git_log
  input:
    base: '{{release.tag}}'
    head: HEAD
- id: notes
  tool_name: map
  input:
    over: '{{commits.commits}}'
    concurrency: 4
    do:
    - id: files
      tool_name: github__tool__git_changed_files
      input:
        base: '{{item.sha}}~1'
        head: '{{item.sha}}'
        prefix: ''
    - id: note
      tool_name: builtin__infer
      input:
        instruction: |-
          Write one release-note line for this commit.
          Subject: {{item.subject}}
          Files changed: {{files.files}}
finish:
  output:
    since: '{{release.tag}}'
    notes: '{{notes.results}}'
```

</RequestExample>

## Plan files

A plan is a YAML file in `./.graph/plans/` or `~/.config/graph/plans/`. It has an `identifier`, a `description` that tells agents when to call it, its `steps`, and a `finish` that says what it returns. Steps read the plan's inputs as `{{input.<field>}}` and earlier results as `{{<id>.<field>}}`, in the [template language](/reference/template-language). See [Plan file](/plans/reference/plan-file) for every field.

## Steps

A step calls one of:

- A catalog tool: `builtin__*`, `user__*`, or an MCP server's `<server>__*`
- Another plan, as `plan__<identifier>`
- A named agent, as `agent__<name>`
- A control step, which the plan runs itself

| Control step | What it does |
| --- | --- |
| [`exit`](/plans/reference/steps/exit) | Ends the plan early, with success or an error |
| [`route`](/plans/reference/steps/route) | Takes one branch of steps |
| [`filter`](/plans/reference/steps/filter) | Keeps the items in a list that pass a condition |
| [`map`](/plans/reference/steps/map) | Runs steps once per item, several at a time with `concurrency` |
| [`reduce`](/plans/reference/steps/reduce) | Folds a list into one value |
| [`agent`](/plans/reference/steps/agent) | Gives one task to an agent with its own prompt and tools |
| [`ask`](/plans/reference/steps/ask) | Asks a person a question mid-run |

Model calls happen only in `agent` steps, model-backed tools such as `builtin__infer`, `infer` and `decide` conditions, and a `solver` finish.

## How a plan ends

`finish` decides what a plan returns:

- `output` returns a map of step results as JSON, with no model call.
- `solver` has a model write the answer from the results.
- `silent` returns nothing, for plans that only act.

## Running plans

- `graph plan run <identifier>` runs a plan from the terminal or a script.
- Agents and other plans call it as `plan__<identifier>`.
- `graph mcp serve` offers it to MCP clients as `plan_<identifier>`.

A failing step fails the run. graph doesn't rewrite a plan you wrote to work around it.

## Where plans live

graph reads `./.graph/plans/` before `~/.config/graph/plans/`, and the first plan with an identifier wins, so a project plan replaces one in your home directory. A plan with a [built-in plan's](/plans/reference/built-in-plans) identifier replaces the built-in. Commit `./.graph/plans/` to give your whole team the same plans.
